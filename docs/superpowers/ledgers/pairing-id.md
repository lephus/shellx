# Pairing ids — cross-plan contract change (controller ruling, 2026-09-26)

## Why
The relay keeps `pairing_removed` as tombstones replayed on every agent connect until the pair is re-created (relay final fix I1), so a re-paired phone is not dropped. The agent side (plan 03 Task 9) then had to ignore tombstones while its own `POST /v1/pairings` was pending. Task 9's review found that design unsound: if POST#1 commits but its response is lost, the phone unpairs (tombstone + live event, ignored because the pairing is "pending"), and POST#2 then clears the tombstone and re-creates the row → the agent trusts a phone the user unpaired, forever, silently. The agent alone cannot tell a stale tombstone from a fresh one. A revoke's DELETE that lands after a quick re-pair's POST can also delete the newer row.

**Ruling:** every pairing gets an id generated by the agent at `pair.confirm`; the relay stores it on the row and on tombstones; events and DELETEs are matched by id. This removes all ordering ambiguity without clocks. Nothing is deployed yet, so the D1 schema change goes straight into `0001_init.sql`.

## Contract (binding; update overview §4/§5 and spec §5.3, §5.5, §10.2, §10.3 to match)
1. D1 `pairings` gains `pairing_id TEXT NOT NULL` (lower-case canonical UUID v4 chosen by the agent). Edit `relay/migrations/0001_init.sql` in place (not yet deployed); keep the table otherwise unchanged.
2. `POST /v1/pairings` (agent token, as today) body `{"mobile_id": "<uuid>", "pairing_id": "<uuid>"}`:
   - `pairing_id` missing or not a UUID → `400` with the existing error envelope and the existing bad-request code.
   - A tombstone exists for (this agent, mobile_id) with the SAME `pairing_id` → `410` with code `pairing_removed`; the row is NOT created and the tombstone stays (the phone unpaired this exact pairing before the relay registered it).
   - Otherwise: clear tombstones for (agent, mobile) whose `pairing_id` differs (they belong to an older pairing), then upsert the row with this `pairing_id` → `201`. Same id again → `201` (idempotent).
   - All existing checks (mobile in caller's account, `device_not_found`, rate limits, body limit) unchanged.
3. `DELETE /v1/pairings/:agent_id/:mobile_id` gains an optional query `?pairing_id=<uuid>`:
   - With it (the agent's revoke): delete only if the row's `pairing_id` matches; otherwise `204` and nothing happens (no tombstone, no event).
   - Without it (the phone's unpair): delete whatever row exists (as today).
   - When a row is deleted: the tombstone stores that row's `pairing_id` (one tombstone per (agent, mobile); a newer deletion overwrites the older tombstone's id), and the live EVENT carries it.
   - Invalid `pairing_id` query value → `400`.
4. EVENT `pairing_removed` gains the text field `"pairing_id": "<uuid>"` (still a minimal text-only CBOR map). Replay rules unchanged: live to both connected parties; tombstone replayed to the agent on every connect after the PRESENCE snapshot; cleared by a POST with a different id, agent logout, account deletion.
5. `GET /v1/devices` / pairing listings: include `pairing_id` only if an existing response already lists pairing rows (check the code; do not add new fields elsewhere).

## `shellx_core` (Dart) — keep everything else unchanged
- `ShellxApi.createPairing(String mobileId, {required String pairingId})` → sends both fields.
- `ShellxApi.deletePairing(String agentId, String mobileId, {String? pairingId})` → adds `?pairing_id=` when given.
- A `410` surfaces as `ApiException` with `status == 410` and `code == 'pairing_removed'` through the existing error mapping (add a test).
- `EventFrame` stays a generic text map; if core has a typed accessor for `pairing_removed`, extend it with `pairingId`; otherwise add nothing.
- Update overview §5 signatures accordingly (they are the binding contract other plans consume).

## Not in this change (done later in plan 03 Task 9's fix round)
Agent-side use of ids (trusted entry stores `pairingId`; events matched by id; POST 410 → drop trust; revoke DELETE with id; pending set only drives retries) and the plan-03 `FakeRelay`.

- relay: `npm ci` (if needed), `npm test` twice all green, `npm run typecheck`; new tests for every rule in 2–4 (410 on same-id tombstone, older-id tombstone cleared by POST, idempotent same-id POST, DELETE with mismatching id is a no-op, DELETE without id deletes any row, event and tombstone carry the id, replay carries the id, logout/deletion purge).
- core: `dart test` in `packages/shellx_core`, `dart analyze --fatal-infos`, `dart format --output=none --set-exit-if-changed .`.

## Follow-up: UUIDv7 ordering (controller ruling on concern 4)

Commits:
- `5554b42` fix(relay): refuse pairing ids not newer than a tombstone
- `ef5f95e` docs: pairing ids are UUIDv7 ordered by the agent's clock

The first relay commit (`22e01bf`) is unchanged. `5554b42` was amended once before this report to fix the migration comment ("UUID v4" → "UUIDv7").

### Rule: pairing ids are UUIDv7, ordered as canonical lower-case strings

**Validation.** New `parseUuidV7` in `relay/src/protocol/uuid.ts`: `parseUuid`, plus version nibble (index 14) === `7`.
- POST `pairing_id` and the DELETE `?pairing_id=` query both use it. Anything else gets `400 bad_request`.
- Applying it to the DELETE query is my own consistency choice: any id that can be stored is v7.
- The variant bits are not checked, as the ruling asked (version nibble only).

**`UserHub.admitPairing`.** It reads the pair's tombstone:
- none → true;
- `tombstone.pairing_id >= pairingId` → false, tombstone kept;
- older → the tombstone is deleted, true.
- It is still called before and after the upsert, with the same comparison.

**Addition 1 — the row guard.** The upsert is now `ON CONFLICT … DO UPDATE … WHERE excluded.pairing_id >= pairings.pairing_id`. If `meta.changes` is 0, the row already holds a newer pairing, so the POST is stale and gets 410. The newer row is kept; the 410 path only deletes a row with this same id.
- Why: without the guard, a stale POST X could overwrite row Z. A later phone unpair would then tombstone X. The agent, holding Z, would ignore that event, and trust in Z would leak.

**Addition 2 — tombstones keep the newest id.** `notifyPairingRemoved` now upserts with `ON CONFLICT … DO UPDATE … WHERE excluded.pairing_id > pending_pairing_removed.pairing_id`. A newer removal overwrites the tombstone; an older one does not.
- Why: a phone DELETE could read an old row X, then notify late, after pairing Z was removed. Overwriting would hide Z's removal from an agent that missed the live event.
- The live event still carries the id of the row actually deleted.
