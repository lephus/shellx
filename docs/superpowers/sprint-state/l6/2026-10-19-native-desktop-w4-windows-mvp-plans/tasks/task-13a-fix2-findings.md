# Task 13a fix round 2 — open findings (from the round-1 re-review; carried across the 07:11 pause)

Scope: `windows/shellx-app/src/remote_session.rs` (and `remote_link.rs` only if needed). NO public API change (13b is built against `SessionConfig`, `SessionStatus`, `RemotePane`, `Want`, `PaneEvent`, `RemoteMirror`, `Applied`). NO UI files. Both findings are load-bearing for 13b.

## F1 (Important): `PaneEvent::Retargeted` is lost after a failed attach that created a terminal
`Worker::attached` (the `Err(fail)` arm) stores `fail.created` into `p.terminal_id` and `p.want = Want::Terminal(created)`. The later successful attach then decides whether to emit `Retargeted` with `p.terminal_id.as_deref() != Some(terminal_id) || !matches!(p.want, Want::Terminal(_))` — which is now false, so the UI never learns the terminal id the Mac created (13b stores it in `PaneTarget::Remote{terminal_id}` from `Retargeted`). Same hazard for any path that records an id before the UI was told.
Required: track "id announced to the sink" separately from "id we want/created" (e.g. a field on `Pane` set only when `Retargeted` was delivered), and emit `Retargeted` on the first successful attach whenever the announced id differs from the attached id. Test (fake host: `create_terminal` succeeds, first `attach` fails, second succeeds): the sink receives exactly one `Retargeted{terminal_id: <created>}`, and `create_terminal` ran once.

## F2 (Important): attempt ids are reused after `Worker::revive`, so a second enrollment can start
`revive()` replaces `self.state` with `ConnState::new()`, whose attempt ids restart at 1, while `enrolling` / `connecting` / `deferred` / in-flight job results from the previous incarnation survive and are matched by attempt id only. A new `Connect{attempt: 1}` after a revive can (a) pass the `self.enrolling.is_some_and(|e| e != attempt)` guard because the stale enrolling attempt has the same number and start a SECOND invitation connect while the first (up to 300 s approval wait) is still running, and (b) accept stale `Minted` / `Linked` / `Attached` / `ViewEnd` results of the old incarnation as if they were the new attempt's.
Required: attempt ids must never repeat within one `RemoteSession` (for example keep a session-wide monotonic base that the new `ConnState` starts from, or tag messages with an incarnation counter — choose the smallest correct change; if `ConnState` must change, keep it additive in `windows/shellx-model/src/remote_state.rs` with a model test), and `revive()` must leave `enrolling`/`deferred` consistent so one invitation still gives one enrollment. Test: open pane, begin an invite connect that blocks (fake connector), close the last pane (Idle stop), open a new pane (revive) before the connect returns → exactly ONE connect call with the invitation; stale results from the old incarnation are ignored; after approval the pane attaches once and the invite file is deleted once.
